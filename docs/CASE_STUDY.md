# 개발 사례

> [문서 안내](README.md) · 개발 사례

## 문제와 목표

과제 탐색을 자동화했지만 안전관리 심사 결과, 기관 메뉴, 다른 산업의 AI 구축 사업까지 수집됐습니다. 필터를 강화하자 연구실과 관련된 공고도 검토 대기로 남았습니다. 공고를 더 많이 수집하는 것과 필요한 공고를 고르는 것을 따로 다뤄야 했습니다.

## 설계에 반영한 기준

| 발견한 문제 | 수정한 내용 | 관련 코드·테스트 |
|---|---|---|
| 마감 공고까지 상세 수집 | 접수 상태를 먼저 확인하고 기간 내 후보만 첨부 분석 | [triage.py](../aclbrief/triage.py), [test_v050.py](../tests/test_v050.py) |
| 기관명이나 배경 설명의 통신 용어로 오탐 발생 | 기관명과 연구 제목을 구분하고, 실제 연구 목표에 통신 기술이 필요한지 확인 | [rule_evidence.py](../aclbrief/rule_evidence.py) |
| 같은 연구 목표 앞에 ‘본 공고의’를 붙이면 보류 | ‘공고’라는 단어만으로 연구 문장을 제외하던 규칙 수정 | [test_v060.py](../tests/test_v060.py) |
| 기업 보험 면제를 대학 신청 제한으로 오인 | 신청 자격과 기업에 주는 부가 혜택 구분 | [test_v060.py](../tests/test_v060.py) |
| 매뉴얼 판독 실패로 공고 전체를 보류 | 공고문·RFP와 매뉴얼·서식·참고 법령을 구분해 오류 처리 | [documents.py](../aclbrief/documents.py) |
| 연구 관련성은 있지만 자격을 확인하지 못한 공고 누락 | 점수를 유지하고 관련 후보로 보관 | [rules.py](../aclbrief/rules.py) |
| 최근 논문이라는 이유만으로 실적을 연결 | 같은 연구 주제 안에서 공고와 실적 제목·초록의 공통 기술 표현을 우선 | [test_v060.py](../tests/test_v060.py) |

## 표현 하나로 추천이 사라진 문제

같은 연구 목표인데 앞에 ‘본 공고의’를 붙이면 점수가 0으로 바뀌는 문제가 있었습니다. ‘공고’라는 단어가 들어간 문장을 연구 근거에서 제외하던 규칙이 원인이었습니다. 문장에 포함된 단어보다 그 문장이 설명하는 연구 목표를 기준으로 판단하도록 수정했습니다.

수정 후에는 같은 가상 공고에서 연구 목표의 표현만 바꿔 점수와 추천 결과가 유지되는지 확인했습니다. 대학 신청 자격을 지운 경우에는 연구 점수를 유지하되 검토 대기로 남는지도 함께 검사합니다. 표현 변경과 자격 누락을 다루는 [회귀 테스트](../tests/test_v060.py)로 두 동작을 확인합니다.

기업에만 보증보험 제출을 면제한다는 문장도 대학의 신청 제한으로 읽혔습니다. 혜택의 대상과 신청 가능한 기관을 구분하도록 바꾸고, 대학 허용 문구가 있는 경우와 없는 경우를 각각 검사했습니다. [가상 공고 예제](../examples/verify_evidence.py)에서 표현 변경·자격 누락·보험 면제의 결과를 비교할 수 있습니다.

## 실행 결과

실제 기록에서 확인한 공고는 **2026년도 AI 기반 주파수 간섭분석 및 전파예측기술 개발사업 신규지원 대상과제 공고**입니다. 2026-11-07 브리핑·진단과 2026-11-09 실행 화면에서 같은 공고가 74점의 관련 후보로 표시됐습니다.

| 기록 | 상세 심사 기록 | 관련 후보 | 확정 추천 |
|---|---|---|---|
| 2026-11-07 브리핑·진단 (v0.6.0) | 4건 | 1건 | 0건 |
| 2026-11-09 실행 화면 | 4건 | 1건 | 0건 |

두 기록 모두 저장 자료는 11,541건입니다. 제목·기간 확인 단계의 자료도 포함하므로, 전체 자료에 대한 상세 분석이나 추천 정확도 측정 결과로 볼 수는 없습니다. [공고 원문](https://www.iris.go.kr/contents/retrieveBsnsAncmView.do?ancmId=024439&ancmPrg=ancmIng) · [실행 화면](SCREENSHOTS.md#실제-공고-검토-사례)

공고를 후보로 찾았지만 판정에는 오류가 남아 있었습니다. 진단에는 대학을 포함한 신청 자격 문구가 있었는데, 기업의 녹색인증에 주는 가점 문장을 필수 기업 주관 조건으로 읽어 자격을 미확인으로 처리했습니다. 통신 연구 근거에도 담당자·연락처가 포함된 사업명이 사용됐습니다. 원문을 확보하는 것뿐 아니라, 각 문장의 역할을 구분하는 과정도 개선해야 한다는 점을 확인했습니다.

연구실 실적과는 인접 기술을 통한 연결만 확인됐고 이미지에 있는 상세 내용도 판독하지 못했습니다. 따라서 자격 판정을 고치더라도 이 기록만으로 추천 여부를 확정하기는 어렵습니다.

## GPT로 문맥을 검토하는 기능 추가

규칙만으로 가점과 필수 자격, 연구 목표와 배경 설명을 구분하기 어려워 GPT API 모드를 추가했습니다. GPT가 공고문과 연구 프로필을 비교하고, 관련성과 신청 조건을 인용문과 함께 반환하도록 구성했습니다.

프로그램은 답변의 인용문, 등록된 연구 주제와 실적의 연결, 마감일을 확인합니다. 확인에 실패하거나 API 오류가 발생하면 검토 대기로 남깁니다. 매뉴얼과 서식은 판정에 사용할 원문에서 제외합니다.

[모의 응답 테스트](../examples/verify_gpt_workflow.py)에서는 정상 인용의 통과, 없는 문장을 인용한 답변의 보류, 자격 미확인 후보의 보관을 확인할 수 있습니다. 실제 GPT 호출로 위 오류가 얼마나 줄어드는지는 앞으로 측정할 예정입니다. [GPT 모드 사용 방법](GPT_API.md)

## 개발 과정과 AI 활용

대상은 통신 분야에서 대학 연구실이 참여할 수 있는 과제로 정했습니다. Windows에서 직접 실행하며 안전관리 심사 결과와 다른 산업의 AI 사업이 섞이는 문제를 확인했고, 마감 확인 → 제목 선별 → 상세 검토 순서로 처리하도록 요구사항을 정리했습니다.

추천이 0건으로 나오자 필터를 단순히 완화하기보다 보류 근거를 살폈습니다. 기업 보험 면제와 신청 자격이 뒤섞인 사례를 바탕으로 두 조건을 구분하도록 했고, 연구 관련성은 있지만 자격이 불명확한 공고는 점수를 유지한 관련 후보로 표시하도록 했습니다. 수정 후에는 진단의 인용문·출처와 회귀 테스트 결과를 대조했습니다.

Python 코드, 웹 UI, 수집·문서 추출 기능과 테스트 작성에는 AI 코딩 도구를 활용했습니다. 저는 탐색 범위와 선별 순서를 정하고, 실제 실행에서 발견한 오류를 바탕으로 수정 방향을 결정했습니다. ‘본 공고의’ 표현을 바꿔 확인하는 테스트처럼 AI와 개발 과정에서 만든 가상 예제도 활용했습니다. 프로그램 실행 중 공고를 검토하는 GPT API 기능은 선택 모드로 추가했으며, 현재 공개된 연동 검사는 모의 응답을 사용합니다.

## 남은 과제

1. 실제 문서에서 가점·우대 조건과 필수 신청 조건을 더 정확히 구분합니다.
2. 담당자·사업 소개·배경 설명을 연구 목표와 구분하는 규칙을 보강합니다.
3. 연결한 실적의 전문을 대조하고, 인접 기술을 해당 과제에 적용할 수 있는지 검토합니다.
4. 미지원 기관의 링크와 페이지 이동 방식을 추가하고 수집 성공률을 측정합니다.
5. 관련·무관 공고에 정답을 붙인 평가 자료를 만들어 추천 정밀도와 재현율을 비교합니다.

버전별 수정 내용은 [변경 이력](CHANGELOG.md), 현재 테스트 결과는 [테스트 기록](VALIDATION.md)에 정리했습니다.
